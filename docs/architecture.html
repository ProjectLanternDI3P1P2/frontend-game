Project Lantern · Front

Architecture front de Project Lantern

Deux applications Nuxt, chacune dans son dépôt, construites pour appliquer les quinze ADR front. C'est un squelette : le socle, la structure et les contrôles qualité sont en place, et les features attendent les squads qui en sont propriétaires.

  • 2 dépôts Git indépendants
  • 15 ADR appliqués
  • 7 + 4 dossiers de features
  • Lint · typecheck · tests · build au vert

Vue d'ensemble

Le public et le jeu ont des besoins de rendu, de cache et de mise en production trop différents pour une seule application (ADR-FE-002). Chacune vit donc dans son propre dépôt, avec sa CI, sa doc et sa copie des ADR (ADR-FE-007) : publier l'une ne demande jamais de publier l'autre.

Flux entre systèmes

Aucun des deux fronts ne détient de données métier. Toute lecture et toute écriture passent par l'API Gateway, via des clients HTTP typés écrits à la main (ADR-FE-011). Les erreurs et les Web Vitals partent vers le point d'entrée d'observabilité fourni par l'équipe Ops (ADR-FE-013).

Ce qui est vérifié en revue

  • Un composant n'appelle jamais la Gateway. Seul le dossier api/ de la feature le fait, via useGateway().

  • Rien ne passe dans shared/ avant d'avoir deux vrais consommateurs et l'accord des squads concernés.

  • On ne modifie pas la feature d'un autre squad sans lui en avoir parlé d'abord.

  • Aucune couleur, taille ou police en dur dans un composant. On utilise un token, et si aucun ne convient, on en ajoute un et on le documente.

État et autorité serveur

Dans le game-client, deux mécanismes cohabitent et ne se confondent pas (ADR-FE-008). Pinia garde ce que le client possède : session, panneau ouvert, file de notifications. useApiResource garde une copie temporaire de ce que le backend possède.

Type d'état Exemple Où il vit
UI éphémère Modale ouverte, filtre, champ de formulaire Local au composant (ref)
Session client Token, identité, panneau latéral Store Pinia session
Retour au joueur Récompense obtenue, action refusée Store Pinia notifications + live region
Données métier Inventaire, progression, run en cours useApiResource(clé, fetcher, ttl)

Le cache évite les requêtes en double (deux écrans qui lisent la même clé partagent le même appel), affiche la péremption grâce à une horloge commune et au badge UiStaleBadge, et se vide entièrement au logout. Il peut rester au niveau du module parce que le client de jeu est en CSR : il ne traverse jamais de requête serveur.

Rendu du site public

Le rendu statique est la règle. Il est peu coûteux, indexable, lisible avant l'exécution du JavaScript et continue de fonctionner si la Gateway tombe. Le SSR est l'exception : il faut dire ce qui change entre deux requêtes et qu'un build ne peut pas connaître (ADR-FE-003).

Forme routeRules Quand l'utiliser
Statique { prerender: true } Par défaut. Contenu qui change à chaque release, pas à chaque requête
SSR + swr { ssr: true, prerender: false, swr: 60 } Données assez fraîches à la minute près et qui doivent rester indexables
SSR sans cache { ssr: true, prerender: false, cache: false } Quand une réponse en cache serait fausse, par exemple le statut des services pendant un incident
CSR — Jamais le mode par défaut ici. C'est le mode du game-client

Une route SSR sans stratégie de cache explicite est refusée en revue. Toute nouvelle route se déclare dans nuxt.config.ts et dans docs/rendering-modes.md. Aujourd'hui, seule / existe, et elle est statique.

Socle partagé

Ce qui existe déjà et qu'aucun squad n'a à réécrire.

shared/utils/gateway.tsles deux

Le seul transport HTTP. Routes versionnées, X-Correlation-Id sur chaque requête, enveloppe d'erreur GatewayError, 204 géré, isOutcomeUncertain.

useApiResource.tsgame-client

Cache de requêtes par clé, avec TTL, jonction des requêtes déjà en cours, invalidation par préfixe et clearApiCache() au logout.

shared/stores/game-client

session garde le token en mémoire et lance la mesure de performance. notifications gère la file lue par la live region.

plugins/telemetry.client.tsles deux

LCP, INP, CLS, erreurs window, rejets de promesses et erreurs Vue, envoyés par lots via sendBeacon. Inactif tant qu'aucun endpoint n'est configuré.

server/routes/healthz.tsles deux

Renvoie { status, app, version, commit, builtAt }, l'identité de build exigée au jalon cycle 1 / semaine 2.

shared/ui/les deux

Primitives en BEM auto-importées : UiButton, UiPanel, plus UiStaleBadge et UiNotificationCenter côté jeu.

Deux règles de lint sont réglées volontairement, avec la justification écrite dans eslint.config.mjs : role="list" est conservé sur les <ul>, parce que Safari/VoiceOver perd la sémantique de liste quand on retire les puces, et <label for> + id compte comme une association valide.

Ajouter une feature

La procédure est la même dans les deux dépôts. Le dossier _template/ reste exécutable et linté pour ne pas se périmer en silence.

  1. Copier le templatecp -r app/features/_template app/features/<nom>, puis renommer example partout.

  2. Écrire types.ts à la maind'après le contrat versionné de la Gateway. Pas de génération OpenAPI (ADR-FE-011).

  3. Mettre chaque appel dans api/C'est le seul fichier de la feature autorisé à joindre la Gateway.

  4. Isoler les règles puresdans un .ts sans framework, testé par Vitest dans tests/ (ADR-FE-012).

  5. Choisir la forme de l'étatLocal si l'état est éphémère, useApiResource avec une clé et un TTL si des données joueur sont partagées entre écrans (ADR-FE-008).

  6. Ajouter la route dans pages/et l'entrée de navigation. Côté public-site, déclarer aussi le mode de rendu et le justifier.

  7. Remplir le README: objectif, routes, APIs consommées, état partagé, squad propriétaire, couverture de tests.

  8. Écrire un parcours Cypressseulement si la feature ajoute un chemin critique. Toutes n'en ont pas besoin.

Volontairement hors périmètre

Écrans

Code de gameplay

Parcours E2E

Auth, démarrer ou reprendre une session, action de jeu : c'est aux squads qui livrent ces routes de les écrire.

Décisions ouvertes

Le brief client demande des choses qu'aucun ADR actuel ne couvre. Elles sont notées dans docs/open-decisions.md et ne doivent pas être tranchées au détour d'une pull request.

bloquant

Transport temps réel pour la coop

Polling, Server-Sent Events ou WebSocket. L'ADR-008 prévoit un cache sur requêtes, qui ne convient pas à un lobby où les actions des autres joueurs doivent apparaître sans intervention. party/ reste vide tant qu'un ADR n'a pas tranché.

à attribuer

Squad propriétaire de party/

La coop concerne les cinq squads, alors que l'ADR-009 en exige un seul. C'est à l'équipe de gouvernance d'attribuer ce dossier.

à décider

Paiement en argent réel dans le store

Choix du prestataire de paiement et du flux de redirection. Aucune donnée de carte ne doit arriver dans nos composants.

à décider

Langue du produit

Anglais pour l'instant (lang="en"), parce que le brief client est rédigé en anglais. Aucun ADR ne fixe ce choix ni l'i18n.
