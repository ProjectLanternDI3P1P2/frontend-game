# Dungeon explorer

> **Owner squad:** Dungeon (ADR-FE-009)

### Purpose

Renders a dungeon generated by the Dungeon service and lets the player explore
it one tile per turn, with the art team's room kits and props, a fog of war and a
room-level minimap. The dungeon itself is never generated here: the service owns
it (ADR-GLOB-011) and the client only draws it (ADR-FE-008).

This feature belongs to the game client (ADR-FE-002, ADR-FE-004). It lives in
this repository until the game client repository exists; moving it means
copying `app/features/dungeon/`, `app/pages/dungeon/` and the route rule.

### Routes

| Route             | Rendering          | Why not static / why not SSR                                                |
| ----------------- | ------------------ | --------------------------------------------------------------------------- |
| `/dungeon`        | CSR (`ssr: false`) | Starts a per-player run: nothing to prerender, nothing to index.            |
| `/dungeon/:runId` | CSR (`ssr: false`) | Keyboard-driven game state; a server render would be replaced on hydration. |

### APIs consumed

| Call               | Gateway route                                    | Cached                                 |
| ------------------ | ------------------------------------------------ | -------------------------------------- |
| `createDungeonRun` | `POST /api/v1/dungeon-runs`                      | never                                  |
| `joinDungeon`      | SignalR `/hubs/dungeons` → `JoinDungeon`         | never: the run is mutable              |
| `moveHero`         | SignalR `/hubs/dungeons` → `MoveHero`            | never                                  |
| `defeatFloorBoss`  | `POST /api/v1/dungeon-runs/{runId}/boss-defeats` | never                                  |
| `fetchDungeonMap`  | `GET /api/v1/dungeons/{seed}/map?floor=n`        | forever: a floor is immutable per seed |

The fog of war survives a reload: the run carries the tiles the hero stood on
(`visitedTiles`), and the explorer reveals around each of them again on arrival
at a floor.

`defeatFloorBoss` is temporary too: it stands in for Combat's fight when the
hero walks into the boss, and Combat calls it once the fight exists.

The Player lobby now owns the normal start flow: it creates the game session,
passes an optional replay seed to Dungeon, then opens `/dungeon/:runId` after
Player returns the created run. The standalone `/dungeon` launcher remains a
development explorer for starting a run directly against Dungeon.

### How it stays fast without an engine or a canvas (ADR-FE-005, ADR-FE-006)

| Concern    | Decision                                                                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Payload    | One text row per tile row plus a sparse element list: ~40 KB per 40-room floor, ~3 KB gzipped, fetched once.                                                                                           |
| Decoding   | Typed arrays (`Uint8Array` cells, `Int16Array` room index), wrapped in `markRaw`: Vue never walks 17,000 tiles.                                                                                        |
| Autotiling | Sprite choice for every tile computed once per floor (~10 ms), as CSS custom properties.                                                                                                               |
| DOM size   | Only revealed tiles inside the camera window exist: ~150–400 elements whatever the floor size.                                                                                                         |
| Moving     | Tiles are keyed by index in world coordinates: a step adds one row or column and removes one; the camera and tokens move with `transform`.                                                             |
| Animation  | Torches, the hero, traps and the boss gate are rows of frames played by CSS `steps()`; mobs float with a CSS animation; nothing runs in JavaScript per frame. Disabled under `prefers-reduced-motion`. |
| Latency    | Moves are predicted with the backend's own walkability rule and confirmed in order; a refusal or a network error re-reads the run (ADR-FE-008).                                                        |
| Next floor | Prefetched as soon as a floor loads, so going through the gate is instant.                                                                                                                             |

### How walls are drawn

The art team's kits (`app/assets/dongeon/kit/`) draw whole rooms, with walls
12 pixels thick that do not follow the 16-pixel grid, while the service sends
walls one tile thick. `npm run assets:dungeon` (`scripts/dungeon-atlas/`) turns
each kit into an atlas of 16 x 16 tiles, in the kit's own colours: wall tops
redrawn for every arrangement of neighbours, faces, floors, grates and columns
cut from the kit. Rerun it after changing a kit: it rewrites the atlases and
`tiles/atlas.generated.ts`.

`tiles/autotile.ts` then follows the kit's three-quarter view:

- a wall with an open tile below it is seen from the front: its brick **face**
  stands on the wall tile and, where the void above leaves room for it, on the
  tile above too, so that rooms are walled as high as in the kit; its top edge
  (**rim**) lies above;
- every other wall is seen from above and shows only its rim;
- a rim is a band of stone that hugs the inside of the dungeon. Its tile is
  chosen from its eight neighbours (another rim, the inside, the void), so
  corners are closed, corridors join rooms cleanly and free ends are rounded;
- a wall closing a room on its south side shows its front edge, and the void
  starts right below it: nothing hangs down into it;
- a wall keeps the same height from one end to the other, and only walls two
  tiles high carry torches, banners and chains;
- every piece of the atlas is padded with a copy of its edges, so that a
  browser zoom never shows a line of its neighbour;
- columns, furniture and the ladder stand upright: they are sorted by row with
  the hero and the mobs (`z-index` from `--y`), so the hero passing behind a
  column is hidden by it;
- the walls hide the hero, the mobs and the furniture behind them or beside
  them, whose sprites are wider and taller than a tile: the hero's weapon and
  shield never stick out over the walls of a corridor, nor over the face of a
  wall it passes through. The lower half of a face hides what stands on its
  row, so that the hero standing in front of a wall is still drawn over it; the
  upper half and the top of a wall hide their row and the row below. The gate
  stands over its wall;
- chests standing as furniture are open: only the chests that hold an item are
  closed. Big furniture (chests, skulls, coins) only stands between two bare
  floor tiles, with nothing right behind it, so that it never covers a wall, a
  column or another piece;
- wall tops are lighter than the flagstones, so that a wall, inner ones
  included, always stands out of the floor. Rooms have no walls one tile thick
  inside them: they read as flat slabs, so the templates use columns instead,
  and columns standing a couple of tiles apart (a colonnade) are short ones;
- water and lava pools ripple: `npm run assets:dungeon` cuts the art team's
  three frames of water into `liquids.png` and recolours them, shade for shade,
  into lava on a second row; CSS plays the frames, and the floor around a pool
  casts its banks on it (`LIQUID_BANKS`, drawn in the atlas in each theme's
  colours);
- tombs lie two or three side by side: the first tile carries the whole tomb,
  bloodied in the lair of a boss; books and potions lie about in storerooms,
  treasuries and start rooms;
- fences use the art team's pieces by role (`FENCES` in `tiles/tileset.ts`):
  rails between fences side by side, the end-on piece where a fence runs north
  to south (its spike at the far end), and a post where it ends or turns, the
  left one or the right one, with the half rail joining it to its run.

Floors take turns between two themes (`themeOf`): violet stone, then brown
stone. The atlases share one layout, so a theme only switches the image.

Dressing, all picked with a hash of (seed, floor, tile) so a replayed seed
looks the same: torches frame the gate down; banners, chains, blood and cobwebs on
wall faces; cracked, broken and dirty flagstones and large slabs; candles and
mushrooms at the foot of the walls. Each room is dressed for what it is:
barrels and vases in the start room, chests and coins in the treasury, rubble
in the empty rooms, bones, skulls, candles and blood in the lair of a boss.

The viewport draws the ground of every tile first, then what stands on it or
hangs over it, so that a banner or a cobweb wider than its tile is never cut by
the next tile. Tiles are 64, 48, 32 or 16 pixels: whole multiples of the art,
never half pixels.

### Floors, bosses and doors

There are no buttons and no stairs: everything happens by walking.

- The party arrives on a floor down a ladder, in the middle of the start room
  (`entrance` in the map). The start room has no door of its own.
- Where a corridor leaves a room northwards, the wall keeps its height on both
  sides of the opening and the corridor goes on between its walls: no arch.
- Each floor ends with a boss, a mob twice the size of the others. Walking into it starts the fight
  (for now, `defeatFloorBoss` records the victory at once).
- The north wall of the boss room holds the `gate` down, drawn as a closed
  portcullis (`gateSprite` in `tiles/sprites.ts`) that rises once
  `floorBossDefeated` is true. Walking into the open gate takes the party to the
  next floor: the move returns the run on its new floor. `goesDown` in
  `dungeonMap.ts` mirrors the backend rule, so a move into a locked gate never
  reaches the server.
- Defeating the boss of the last floor, which has no gate, wins the run.

The hero is a Mana Seed paper doll (`tiles/hero.ts`): a body, an outfit, hair,
maybe a hat, a weapon and a shield, each on its own sheet, stacked in one window
that plays the same frames. It stands on guard and shuffles between tiles with
its weapon drawn, facing the way it last tried to go in all four directions; the
weapon and the shield pass in front of or behind the body with the facing, as
the art's layer order guides say. Headwear hides the hair, which would stick out
of it. Until the run receives the hero from the
Player service, its look is drawn at random from the run id
(`heroAppearanceOf`): a new dungeon, a new hero, the same one on every floor and
after a reload.

Other characters come from the objects sheet: items are chests, chosen by
the element's id, and traps spikes. Every enemy, the boss included (twice the
size), is the art team's `placeholder_mob.png` for now: a single image, so it
floats above its tile over a shadow that stays on the floor.

### Accessibility (ADR-FE-015)

The board is a documented gameplay exception: a focusable `role="application"`
region that takes the arrow keys, described by instructions reserved for
assistive technology. On touch screens every move is also a button (the pad is
hidden when a fine pointer and a keyboard are available). Room changes, blocked
moves and elements underfoot are announced through a polite live region.

The exploration screen uses the full-screen `game` layout: the view is sized to
the window by `fitViewport` (`dungeonRules.ts`, via `useBoardViewport`), and the
HUD, the minimap and the actions float over the board.
